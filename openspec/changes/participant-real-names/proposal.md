## Why

Participants currently join under an auto-assigned fictional name (LOTR / character pools), so the host has no reliable record of who actually attended. Trainers need a real attendance sheet (an auto-generated, downloadable `attendees.md`) without losing the low-friction, privacy-friendly option of joining anonymously. This change collects each participant's real name at join time via a **single free-text field**, keeps an anonymous escape hatch, **warns but never blocks** on duplicate names, **broadcasts the participant name list live (UUID-free) to all participants** so each person can see and resolve their own duplicate, and keeps a live `attendees.md` regenerated from the roster on every name change.

## What Changes

- **Join-time name gate (phase 1).** Before the socket connects — whenever the server has **no committed name for this UUID in the active session** (first visit and next-day / new-session; **not** on same-session reconnect) — show a name screen with a **single free-text name input** (ghost/placeholder text + a short hint that the name will be used to produce the attendance sheet) and two buttons:
  - **Enter** — enabled only when the input is non-empty; submits the typed name.
  - **Anonymous** ("Enter as anonymous") — **ignores** whatever is typed and assigns a fictional name via the existing empty-body register path (`daemon/participant/router.py:515-538`); shows a warning on hover **and** as a tooltip ("You might not appear correctly in the attendance sheet.").
  - The name is stored as a single string in the existing `name` field. There is **no first/last split** in model, UI, or storage. The field cap is raised 32 → 64.
- **Uniqueness checked only on Enter, never blocking (phase 1) — BREAKING behavior change.** On Enter, the server checks the typed name against current participants and returns a duplicate flag in the response, but **always admits** the participant. The old hard **409** blocks in `register` (:511-513) and `rename` (:604-606) are removed. There is **no** live-while-typing check and **no** "are you sure" confirm dialog (both dropped from the prior draft).
- **In-session live duplicate indicator (phase 1).** While a participant's name duplicates another name in the participant list, **their own** name display (profile card at the bottom) shows: a slow red **blink** + a small persistent **underline** + a **⚠️** warning-emoji prefix + the label **"duplicate"** + a **"click here to change"** affordance (which invokes the existing edit crayon / `_startNameEdit`/`_commitName`, `participant.html:3221/3235`). Duplication is detected by **counting occurrences of the participant's own name** in the broadcast name list (≥2 ⇒ duplicate) — **no UUID needed**. The indicator clears automatically for **both** the participant and the previously-conflicting one when the name becomes unique, because both recompute from the re-broadcast list.
- **Participant-list name broadcast (phase 1) — KEY REQUIREMENT + SECURITY, net-new.** Broadcast the participant **names** to **all** participants on **any** change (join / rename / leave), not just the count. Today there is no participant-facing name broadcast (only host-facing `notify_host`), so add a participant-facing message (`participant_names_updated`, a list of **display names only**) via `broadcast()` (`daemon/ws_publish.py:55`); the participant client handles it in `_handleWsMessage` (`participant.html:3914`). The payload **MUST NEVER include UUIDs or any stable per-user id** — a leaked UUID lets one participant impersonate another (the `X-Participant-ID` header is the identity) and bypass rate-limiting / identity. An explicit task **audits all participant-facing WS/HTTP payloads** for UUID/id leakage and strips any found. (The host roster may keep UUIDs — the host is trusted.)
- **Returning participants (phase 1).** A returning participant does **not** see the gate again within the same session — the name is bound to the UUID server-side; on rejoin the server returns their name and the client skips the gate. The gate reappears next day / new session (participant state reset at `daemon/__main__.py:1209-1272`).
- **Live `attendees.md` per session (phase 1).** On **every** name set/change, always **fully regenerate** the whole `attendees.md` from the live roster (no managed-region logic). Written via `atomic_write()` into `get_active_session_folder()`; header derived from the folder name + `_SESSION_FOLDER_RE` date(s) + optional gdrive url; created/cleared at per-session init. Names must round-trip through `participant_state` / `sync_from_restore` / `session-state.json` to survive reconnect.
- **Host download + PDF (phase 2, LATER).** A host UI action downloads `attendees.md` and renders it as a PDF client-side (reusing the `marked` + `window.print()` pattern), backed by a host endpoint serving the Markdown. Explicitly deferred; kept out of the phase-1 task list.

## Capabilities

### New Capabilities
- `participant-real-name-join`: The join-time name gate — a single free-text name input, an **Enter** button (submits the typed name), an **Anonymous** button (ignores the input, uses the fictional-name path, warns on hover/tooltip), the gate-visibility rule (shown when the server has no committed name for this UUID in the active session; skipped on same-session reconnect and for returning named participants), and the 32 → 64 name-field cap.
- `participant-duplicate-name-handling`: Uniqueness checked **only on Enter**, server-side; duplicates are **reported (flag) but never blocked** (no 409 in `register`/`rename`); the **in-session live duplicate indicator** on the participant's own profile card (blink + underline + ⚠️ + "duplicate" + click-to-change), detected by counting the own name's occurrences in the broadcast list and auto-clearing for both sides when unique.
- `participant-name-broadcast`: The net-new participant-facing broadcast of the roster's **display names only** on any join/rename/leave, and the **security invariant** that no participant-facing payload may contain a UUID or other stable per-user id, plus the audit of existing participant-facing payloads.
- `session-attendees-file`: The `attendees.md` lifecycle — always full regeneration from the live roster on every name set/change, header derived from session context, per-session (re)init create/clear, and name persistence round-trip so entries survive reconnect.
- `host-attendees-pdf` (LATER / phase 2): Host endpoint to serve `attendees.md` and client-side Markdown-to-PDF rendering for a printable attendance sheet.

### Modified Capabilities
- None. (The `session` spec that nominally covers "Participant Identity" is an unelaborated stub with no existing requirements, so this change introduces standalone capabilities rather than deltas, matching the precedent set by `persist-session-state-storage`.)
